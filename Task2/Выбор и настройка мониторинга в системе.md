# Мотивация

Чтобы сделать приложение более надёжным и устойчивым к сбоям.\
Как понять, что с приложением все не очень хорошо?\
Сейчас о проблемах сообщают пользователи или представители бизнеса. Это сказывается на репутации компании.\
Нужно работать на опережение и самим первыми обнаруживать проблемы, поэтому лучше самостоятельно следить за состоянием приложения.

# Выбор подхода к мониторингу

- Для очередей - USE
- Для MES - RED
- Для API - Четыре золотых сигнала

# Метрики

1. Number of dead-letter-exchange letters in RabbitMQ - куда перенаправлять сообщения, которые не смогли обработать получатели в обычных очередях.
Перенаправленные в DLQ сообщения будут храниться там для дальнейшей диагностики и больше не будут мешать работе приложений.
Если сообщение не удается считать из очереди после заданного количества попыток, то его можно перенаправить в DLQ.
Количество попыток считывания и идентификатор DLQ определяются политикой перенаправления, установленной для очереди из которой будут перемещаться сообщения. 
2. Number of message in flight in RabbitMQ - сколько сообщений в пути, которые ещё не были подтверждены приложением 
3. Number of requests (RPS) for internet shop API - чтобы видеть количество выполняемых запросов 
4. Number of requests (RPS) for CRM API - чтобы видеть количество выполняемых запросов 
5. Number of requests (RPS) for MES API - чтобы видеть количество выполняемых запросов 
6. CPU % for shop API - сколько использует API 
7. CPU % for CRM API - сколько использует API 
8. CPU % for MES API - сколько использует API 
9. Memory Utilisation for shop db instance - расход инстансом БД 
10. Memory Utilisation for MES db instance - расход инстансом БД 
11. Number of HTTP 500 for shop API - для обнаружения проблем с запросами 
12. Number of HTTP 500 for CRM API - для обнаружения проблем с запросами 
13. Number of HTTP 500 for MES API - для обнаружения проблем с запросами 
14. Number of HTTP 500 for shop API - для обнаружения проблем с запросами
